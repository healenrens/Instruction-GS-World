# Dynamic Video Gaussian Field Plan

## Correction

The target data source is not a static scene scan and not a set of synthetic fixed
scan cameras. The robot data has:

- one fixed head camera;
- one wrist camera whose pose may change with the robot arm;
- a full manipulation video from these cameras.

The target representation is a flowing dynamic Gaussian field. Gaussian identity
should persist through time, while positions/rotations and possibly scale or
semantic state evolve through time. The previous Stage-B fixed multiview canonical
proof only validates that fixed Gaussian IDs are learnable; it is not the final data
generation method requested here.

## What The References Actually Do

### Dynamic 3D Gaussians

Dynamic 3D Gaussians train a persistent dynamic representation from synchronized
multi-view video. Gaussian number, color, opacity, and size persist through time,
while each Gaussian has a per-timestep 3D center and rotation. Training uses
differentiable rendering against input camera images plus physical regularizers:
image reconstruction, local rigidity, local rotational similarity, long-term local
isometry, and optional foreground/background terms. Densification is used only at
the first timestep; after that the Gaussian count stays fixed.

Important limitation: the paper explicitly requires a multi-camera setup and says it
does not work off-the-shelf on monocular video. For our two-camera robot setup, this
means we must provide reliable head and wrist camera calibration/poses and should
not pretend a single fixed head view is enough for this exact method without extra
priors.

### 4-LEGS

4-LEGS does not replace the dynamic RGB reconstruction. Its pipeline first trains a
Dynamic 3DGS model, extracts spatio-temporal features from the input multiview
videos using ViCLIP, trains an autoencoder, and then trains a 4D language embedded
Gaussian field. The semantic features are distilled into the pretrained dynamic
Gaussian representation by rendering Gaussian features and matching pixel-aligned
video-language features.

For this project, 4-LEGS is a reference for the semantic/language feature layer
after the dynamic RGB Gaussian field exists. It is not evidence for building a
static canonical scene or for using artificial fixed scan cameras.

### 4D LangSplat

4D LangSplat first trains a 4D-GS RGB dynamic scene model. That model has deformable
Gaussian points and a deformable decoder that changes Gaussian position, rotation,
and scale over time. Then it adds two language fields:

- time-agnostic semantics, learned with SAM/CLIP as in LangSplat;
- time-varying object-level language, obtained from SAM masks, DEVA video mask
  tracking, multimodal LLM captions, and LLM embeddings.

Its key lesson for us is that language should be attached to a dynamic 4D Gaussian
field after RGB dynamics reconstruction, and the time-varying language should be
object-wise or mask-track-wise rather than per-frame independent.

### DGD And Deformable 3DGS

DGD and Deformable 3DGS are closer to sparse or monocular video conditions. They
use a canonical Gaussian field plus a deformation model indexed by time. The model
predicts per-Gaussian changes such as position, rotation, and scale from Gaussian
position and time. DGD additionally distills dynamic semantic features into this
dynamic Gaussian representation.

These methods are more relevant than pure Dynamic 3D Gaussians if the head+wrist
views are too sparse for a multi-camera persistent-position optimization.

## Correct Project Data Pipeline

The input observation set should be all synchronized frames from the fixed head
camera and the wrist camera:

```text
head_rgb[t], wrist_rgb[t]
head_K, wrist_K
T_world_head
T_world_wrist[t] from hand-eye calibration + robot FK, or from a verified pose solver
optional depth/masks/semantic tracks
```

The dynamic Gaussian field target should be generated by optimizing against both
camera streams:

```text
for each episode:
    initialize Gaussian field from depth/SfM/foundation geometry
    train RGB dynamic Gaussian field over all t and both cameras
    keep Gaussian identity persistent through time
    add language/semantic fields using 4-LEGS or 4D LangSplat style distillation
    export G_i(t) parameters and camera/render metadata for model training
```

Candidate representation choices:

1. **Dynamic-3DGS-style persistent state:** store `x_i[t]` and `q_i[t]`, with
   color/opacity/scale persistent. Use if two views plus calibration and masks are
   strong enough.
2. **Deformable/DGD-style canonical plus deformation field:** store canonical
   `G_i(0)` and a learned deformation `D(x_i, t)` that yields `x_i(t), q_i(t),
   s_i(t)`. Use if the views are sparse and the scene needs a stronger temporal
   prior.

Both choices satisfy the user's core requirement: a flowing dynamic Gaussian field
from videos, with persistent Gaussian identity. Neither choice allows per-frame
independent 3DGS followed by correspondence matching.

## Official Code Data Contracts Checked

### Dynamic3DGaussians / 4-LEGS Contract

The official Dynamic3DGaussians code is the cleanest first target for our
head+wrist setup because its metadata is explicitly indexed by timestep and
camera:

```text
data/<sequence>/
    train_meta.json
    ims/<frame>.jpg
    seg/<frame>.png
    init_pt_cld.npz
```

`train_meta.json` must contain:

```text
w, h
fn[t][c]   image filename for timestep t and camera c
k[t][c]    intrinsics for timestep t and camera c
w2c[t][c]  world-to-camera matrix for timestep t and camera c
cam_id[t][c] stable camera ids for 4DGS/4D-LangSplat Panoptic loaders
```

For this project, `c=0` should be the fixed head camera and `c=1` should be the
wrist camera. The head `w2c[t][0]` can stay constant; the wrist `w2c[t][1]` must
change with robot motion. If an episode has `T` synchronized frames, the
reconstruction sees `2T` real observations, not 4 images and not invented
virtual views.

`init_pt_cld.npz` stores an array named `data` with columns:

```text
x, y, z, r, g, b, foreground_seg
```

This initial cloud must come from real geometry evidence: calibrated depth,
robot/world geometry, multi-view triangulation across valid head/wrist frames,
or another verified geometry initializer. It should not be a static canonical
scan invented from simulator-only views.

The official training loop first optimizes timestep 0 with densification, then
keeps Gaussian count fixed and updates per-timestep centers/rotations using RGB,
segmentation, rigidity, rotation, isometry, floor, background-static, and color
consistency losses. This is the desired "flowing Gaussian field" behavior.

4-LEGS keeps this same data contract. It first runs its D3DGS pretraining, then:

```text
extract ViCLIP features over local video clips around each timestep/camera
train an autoencoder over those features
train per-Gaussian LEGS features on top of the pretrained dynamic scene
```

So 4-LEGS is the semantic/language layer after a dynamic RGB Gaussian field has
already been reconstructed. Its D3DGS pretraining path supports all cameras, but
the current semantic-stage loader should be audited before claiming two-view
language-feature training.

### 4DGS / Deformable / DGD Contract

4DGS and Deformable-style methods are also valid references, but the loader
choice matters:

- 4DGS `multipleview` expects fixed camera folders like `cam01/frame_00001.jpg`
  and one COLMAP pose per camera. That branch does not directly express a wrist
  camera whose pose changes every frame.
- 4DGS/Deformable `transforms_train.json` style loaders use a per-frame
  `transform_matrix` plus `time`/`fid`. That can express head and wrist frames as
  separate observations at the same timestamp if we provide calibrated per-frame
  poses.
- DGD follows the Deformable 3DGS pattern and adds per-Gaussian semantic feature
  optimization with DINOv2 or LSeg-CLIP features between its semantic start/stop
  iterations.

This means Deformable/DGD are better fallback references if two views are too
sparse for direct D3DGS per-timestep state optimization, but they still require
all video frames, calibrated camera poses, timestamps, and an initial point cloud.

## Current Reference-Faithful Recommendation

Start with Dynamic3DGaussians/4-LEGS data conversion because it directly matches
the user's wording: synchronized multiview video becomes persistent dynamic
Gaussians with per-timestep motion. The first episode conversion should produce:

```text
ims/head_000000.jpg ... head_000{T-1}.jpg
ims/wrist_000000.jpg ... wrist_000{T-1}.jpg
seg/head_000000.png ... seg/wrist_000{T-1}.png
train_meta.json with fn/k/w2c for both streams at every timestep
test_meta.json with the same schema for 4DGS/4D-LangSplat Panoptic loaders
init_pt_cld.npz from verified geometry
```

Only after the RGB dynamic reconstruction renders both head and wrist views
reasonably should semantic/language features be attached through 4-LEGS or a
DGD/4D-LangSplat-style distillation path.

Project-side conversion entry:

```bash
python code/scripts/convert_head_wrist_to_d3dgs.py \
  --manifest <episode_manifest.json> \
  --out_root <Dynamic3DGaussians>/data \
  --sequence <sequence_name> \
  --overwrite
```

Minimal manifest schema:

```text
{
  "init_pt_cld": "path/to/init_cloud.npz",
  "cameras": {
    "head": {"K": [[...]], "w2c": [[...]]},
    "wrist": {"K": [[...]]}
  },
  "frames": [
    {
      "head": {"rgb": "...", "seg": "..."},
      "wrist": {"rgb": "...", "seg": "...", "w2c": [[...]]}
    }
  ]
}
```

Frame-level `K` and `w2c` override camera defaults. The converter deliberately
does not infer missing poses or geometry. It writes masks as 0/1 PNGs because
official D3DGS reads segmentation values without dividing by 255.
It writes `cam_id` and `test_meta.json`; without manifest `test_frames`, the
test file mirrors train only for loader compatibility, not held-out metrics.

## Non-Negotiable Implementation Rules

- Do not use the previous 4-fixed-scan-camera Stage-B generator as the final method.
- Do not fuse action-video frames into a static `g0`.
- Do not reconstruct every frame independently and register Gaussians afterward.
- Do not invent virtual views or assume many cameras unless they exist in the data.
- Do not implement a simplified point-cloud splat builder as a substitute for the
  referenced dynamic Gaussian optimization.
- Camera pose calibration is part of the data contract, not a detail to ignore.
- Semantic/language features should be added after the RGB dynamic field is stable,
  following 4-LEGS or 4D LangSplat style distillation.

## Next Implementation Gate

Before writing the production data generator, run one reference-faithful miniature
reconstruction:

1. Pick one short episode segment with synchronized head and wrist videos.
2. Verify intrinsics, time sync, and `T_world_wrist[t]`.
3. Convert the segment into the input format of a selected reference implementation
   (Dynamic 3DGS if calibration/views are sufficient; DGD/Deformable if sparse).
4. Train the official dynamic Gaussian reconstruction on that segment.
5. Verify render quality on both head and wrist views.
6. Export `G_i(t)` and inspect whether Gaussian identity is persistent.
7. Only after that, adapt the project trainer to consume this dynamic field target.

The earlier Stage-B sim proof remains useful as evidence that fixed-ID trajectories
are learnable, but it must not be mistaken for the requested data generation method.
